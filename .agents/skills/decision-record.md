# Decision Records

ADR と RDR は、単に「何を決めたか」だけでなく、なぜその判断に至ったかを、
将来の開発者が追跡できる形で残すための記録である。

## 使い分け

### ADR

ADR は、システムの構造・技術・実装方針に関する意思決定を記録する。

対象の例：

- システム構成
- コンポーネントやサービスの分割
- API の設計方針
- データモデル
- 認証・認可方式
- 外部サービスやライブラリの採用
- データベースの選択
- 非同期処理やメッセージング方式
- デプロイ方式
- セキュリティ・可用性・性能に関する設計
- 技術的制約への対応方針

### RDR

RDR は、要求・仕様・業務ルールに関する意思決定を記録する。

対象の例：

- ユーザーが何をできる必要があるか
- 業務ルールや制約
- 対応する利用者・権限の範囲
- 入力値・出力値・状態遷移
- エラー時の振る舞い
- 非機能要求の目標値
- 法令・規約・社内ルールへの対応
- 要求の優先順位
- 要求間のトレードオフ
- 曖昧な要求の解釈
- 要求を採用しない、または延期する判断

技術的な実現方法を決める場合は ADR、満たすべき振る舞いや制約を決める場合は RDR とする。
両方にまたがる場合は、要求側を RDR、実現方法を ADR に分け、相互にリンクする。

## 新しいレコードを作るとき

次のいずれかに該当する場合は、新しいレコードを作成する。

- 複数の合理的な選択肢が存在する
- 後から変更するとコストが高い
- 複数の担当者・チーム・システムに影響する
- 将来、判断理由を説明する必要がありそうである
- 既存のレコードを無効化または大きく変更する
- セキュリティ、法令、費用、可用性、性能、運用に影響する
- チーム内で議論や合意形成が必要になった
- 要求や仕様の曖昧さを解消するために解釈を固定する
- 「なぜこの方法なのか」をコードだけでは説明できない
- 同じ論点について、将来再び議論される可能性がある

特に、次のような変更はレコード化を優先する。

- 認証方式を変更する
- データの所有者や保存場所を変更する
- API の互換性に影響する変更を行う
- 外部サービスや主要ライブラリを採用・廃止する
- 要求の優先順位や対象ユーザーを変更する
- 法的・契約的・監査上の意味が変わる
- 障害やインシデントを受けて設計方針を変更する

## 新しいレコードを作らなくてよい場合

次のような変更は、通常は新しいレコードを作らない。

- 既存の決定に従った単純な実装
- typo、表記、コメントの修正
- コード内部のリファクタリングで外部仕様が変わらないもの
- 既存の決定をそのまま適用する設定変更
- すでに決定済みの内容を別の文書に転記するだけの作業
- 一時的な調査や実験。ただし、正式な方針決定につながった場合は記録する

判断に迷う場合は、レコードを作る。
短いレコードを作るコストは、後から判断理由を再調査するコストより小さいことが多い。

## 1レコード1決定

1つのレコードには、原則として1つの主要な意思決定だけを記録する。

悪い例：

- 認証方式、DB 選定、ログ設計を1つのレコードにまとめる

よい例：

- Microsoft Entra ID を認証基盤として採用する
- PostgreSQL を永続化ストアとして採用する
- 認証イベントを監査ログに記録する

ただし、複数の判断が不可分であり、常に同時に変更される場合はまとめてもよい。
その場合は、本文中で各判断と依存関係を明示する。

## ファイル名と番号

ファイル名は、連番と短い説明を組み合わせる。

例：

```text
docs/decisions/ADR-0001-use-entra-id.md
docs/decisions/ADR-0002-use-postgresql.md
docs/decisions/RDR-0001-invite-only-registration.md
```

- 番号は一度付けたら再利用しない
- 番号は作成順に割り当てる
- 種別ごとに連番にしても、全体で連番にしてもよい
- プロジェクト内で一度決めた命名規則は維持する
- ファイル名は短く、決定内容が推測できるものにする
- 決定が後から変更されても、元のファイル名は変更しない

## 基本テンプレート

```md
# ADR-XXXX: [決定内容]

- 種別: ADR
- ステータス: Proposed
- 作成日: YYYY-MM-DD
- 更新日: YYYY-MM-DD
- 作成者: [名前またはチーム]
- 関連: [Issue、PR、RDR、ADR へのリンク]

## コンテキスト

なぜこの判断が必要になったのかを書く。

以下を含める：

- 解決すべき問題
- 背景
- 現在の状況
- 前提条件
- 制約
- 関係する要求
- 判断しない場合に発生する問題

このセクションでは、まだ決定内容を書き始めない。
読者が「なぜ今この判断が必要なのか」を理解できることを重視する。

## 決定

何を採用するかを一文で明確に書く。

例：

> 本システムでは、認証基盤として Microsoft Entra ID を採用する。

必要に応じて、適用範囲や例外も記載する。

## 選択肢

検討した選択肢を列挙する。

### 選択肢 A: [名称]

概要、利点、欠点、適用条件を書く。

### 選択肢 B: [名称]

概要、利点、欠点、適用条件を書く。

### 選択肢 C: [名称]

概要、利点、欠点、適用条件を書く。

検討しなかった有力な選択肢がある場合は、その理由も記録する。

## 判断理由

なぜ決定を採用したのかを書く。

比較の観点の例：

- 要求への適合性
- セキュリティ
- 可用性
- 性能
- 拡張性
- 運用負荷
- 開発コスト
- 導入コスト
- 将来の変更容易性
- 既存システムとの整合性
- 法令・契約・監査要件

単に「最もよいから」と書かず、プロジェクト固有の理由を記録する。

## 影響

この決定によって生じる影響を書く。

### 利点

- [利点]

### 欠点・トレードオフ

- [欠点]

### 必要な作業

- [実装・移行・運用作業]

### 影響を受ける範囲

- [コンポーネント、チーム、ユーザー、業務]

## 未解決事項

決定時点で未確定の事項を列挙する。

- [未解決事項]
- [別途決める必要がある事項]

未解決事項を放置しない。
必要であれば、別の ADR または RDR を作成する。

## 見直し条件

この決定を再評価する条件を書く。

例：

- 利用ユーザー数が [数値] を超えた場合
- 外部サービスの料金体系が変更された場合
- セキュリティ要件が変更された場合
- 可用性要件が変更された場合
- 関連する法令・規約が変更された場合
- 実測性能が目標値を満たさない場合
- 前提となった技術が廃止された場合

## ステータス履歴

| 日付 | ステータス | 内容 |
|---|---|---|
| YYYY-MM-DD | Proposed | 初回作成 |
| YYYY-MM-DD | Accepted | 採用を決定 |
```

## RDR テンプレート

```md
# RDR-XXXX: [要求・仕様上の決定]

- 種別: RDR
- ステータス: Proposed
- 作成日: YYYY-MM-DD
- 更新日: YYYY-MM-DD
- 作成者: [名前またはチーム]
- 関連: [Issue、PR、ADR へのリンク]

## 背景

どの要求、業務上の問題、利用者の課題を解決する必要があるかを書く。

## 問題となっている要求

曖昧さ、対立、制約、未決定事項を具体的に記載する。

## 決定

採用する要求または仕様を明確に記載する。

例：

> 未認証ユーザーはアカウントを作成できず、管理者からの招待を受けたユーザーだけが登録できる。

## 対象範囲

- 対象ユーザー
- 対象業務
- 対象画面・API
- 対象外

## 仕様

必要な振る舞いを、テスト可能な形で記述する。

- 前提条件
- 入力
- 処理
- 出力
- 状態遷移
- エラー時の振る舞い
- 権限
- 境界値
- 非機能条件

## 判断理由

なぜこの要求・仕様を採用したのかを書く。

## 影響

- 利用者への影響
- 業務への影響
- 実装への影響
- 運用への影響
- 既存仕様との関係

## 関連する ADR

この要求を実現するための技術的決定をリンクする。

- [ADR-XXXX](./ADR-XXXX-example.md)

## 見直し条件

要求を再評価する条件を書く。

## ステータス履歴

| 日付 | ステータス | 内容 |
|---|---|---|
| YYYY-MM-DD | Proposed | 初回作成 |
```

## ステータス

使用するステータスは、プロジェクトで統一する。

推奨するステータス：

- `Proposed`: 提案中。まだ正式決定ではない
- `Accepted`: 採用済み。実装・運用の基準とする
- `Rejected`: 検討したが採用しなかった
- `Superseded`: 後続レコードによって置き換えられた
- `Deprecated`: 現在は有効だが、利用を終了する方針
- `Amended`: 決定の一部を修正した
- `Withdrawn`: 前提がなくなり、取り下げた

`Accepted` のレコードを直接書き換えて履歴を消してはいけない。
決定が変わった場合は、原則として新しいレコードを作成する。

## 決定を変更するとき

既存の決定と異なる方針を採用する場合は、次の手順を行う。

1. 既存レコードを特定する
2. 既存の決定が現在も妥当か確認する
3. 変更理由と新しい前提を整理する
4. 新しい ADR または RDR を作成する
5. 新しいレコードから旧レコードへリンクする
6. 旧レコードのステータスを `Superseded` または `Amended` に変更する
7. 影響を受ける文書・コード・運用手順を更新する

新しいレコードには、少なくとも次を記載する。

```md
## 置き換える決定

このレコードは [ADR-XXXX](./ADR-XXXX-example.md) を置き換える。

## 変更理由

- [以前の前提が変わった]
- [以前の方式で問題が発生した]
- [新しい要求が追加された]
```

## 書き方の原則

### 決定と理由を分ける

「何を決めたか」と「なぜ決めたか」を別のセクションにする。

### 事実と判断を分ける

- 事実：現在のシステムは Google OAuth に依存している
- 判断：新規登録には Microsoft Entra ID を使用する

### 後知恵で書き換えない

当時利用できた情報と前提に基づく判断を記録する。
後から見て最適でなかったとしても、元の判断理由を消さない。

### 具体的に書く

悪い例：

> 保守性のため、この方式を採用する。

よい例：

> 既存の .NET サービスが利用する標準ミドルウェアと統合でき、
> 独自の認証処理を実装せずに監査ログとトークン検証を統一できるため、
> この方式を採用する。

### 未来の読者を想定する

レコードを読む人が、当時の議論に参加していなくても理解できるようにする。

### 不採用の選択肢も記録する

採用した案だけでは、他の案がなぜ排除されたか分からない。
重要な不採用案と、その理由を記録する。

### 数値と条件を使う

可能なら、次のような具体的な情報を使う。

- レスポンスタイム
- 可用性
- データ量
- 利用ユーザー数
- コスト
- 保持期間
- 対応バージョン
- 法令上の期限
- 再評価の閾値

## 作成手順

新しい意思決定が発生したら、次の順番で進める。

1. 論点を一文で表現する
2. ADR か RDR かを分類する
3. 背景と制約を整理する
4. 主要な選択肢を列挙する
5. 判断基準を明示する
6. 決定と理由を記載する
7. 影響と未解決事項を記載する
8. 関連するレコードをリンクする
9. レビューを受ける
10. ステータスを更新する

## レビュー時の確認項目

レビューでは、次を確認する。

- 決定が一文で理解できるか
- ADR と RDR の分類は適切か
- 背景と問題が明確か
- 重要な選択肢を検討しているか
- 判断理由がプロジェクト固有か
- 影響とトレードオフが書かれているか
- 未解決事項が明示されているか
- 見直し条件があるか
- 関連するレコードがリンクされているか
- 既存のレコードと矛盾していないか
- 後から変更履歴を追跡できるか

## レコード作成の判断例

### 例1: 認証基盤の変更

「Google、GitHub、LINE のソーシャルログインをどのように統合するか」は ADR の対象である。

認証基盤、トークン検証、ユーザー統合、アカウント重複の扱いなど、技術構成に関する選択肢と判断理由を記録する。

### 例2: 招待制登録

「一般ユーザーの自由登録を許可するか、管理者招待制にするか」は RDR の対象である。

対象ユーザー、登録条件、招待の有効期限、重複登録、エラー時の振る舞いを仕様として記録する。

### 例3: API のページング方式

「ページングを offset 方式にするか cursor 方式にするか」は ADR の対象である。

一方、「一覧 API は最大 100 件を返し、追加取得には次ページトークンを使用する」は RDR として記録できる。

### 例4: 単純な実装

既に「API は cursor 方式を採用する」と決定済みで、その方針に従って新しいエンドポイントを実装するだけなら、新しい ADR は通常不要である。

## 最終チェック

レコードをコミットする前に、次を確認する。

- [ ] これは将来参照される意思決定か
- [ ] 1レコード1決定になっているか
- [ ] ADR と RDR を適切に使い分けているか
- [ ] 決定を一文で説明できるか
- [ ] 背景、選択肢、理由、影響があるか
- [ ] 不採用案を必要に応じて記録しているか
- [ ] 未解決事項と見直し条件があるか
- [ ] 関連レコードへのリンクがあるか
- [ ] 既存レコードを不用意に上書きしていないか
- [ ] 将来の読者が、当時の判断を再現できるか
